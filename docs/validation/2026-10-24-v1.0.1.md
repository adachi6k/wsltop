# v1.0.1 release preparation — 2026-10-24

## Scope and compatibility

This patch restores WSL Containers (WSLC) monitoring with WSL/WSLC 3.0.3 and
retries a transiently inconsistent initial Windows host CPU measurement once.
It retains the existing CLI, JSON fields and units, and read-only MCP tools.
Successful empty WSLC measurements now report zero; missing executables,
malformed output and incomplete measurements remain unavailable. Existing
Hyper-V partition validation is unchanged, and persistent inconsistencies are
not clamped or rescaled.

The candidate starts from `c29b3be` on `main`, including the existing lockfile
updates. `Cargo.toml`, `Cargo.lock` and the changelog select version `1.0.1`.
The changelog date records preparation; update it if publication occurs later.

## Real-host investigation and checks

The fixes were exercised on Windows 11 build 26200.9711 with 16 logical CPUs,
Ubuntu 24.04.4 LTS, WSL/WSLC 3.0.3.0 and kernel 6.18.54.1-1. The investigation
checks below preceded the version-only bump and latest lockfile updates;
candidate and exact-artifact checks cover that final dependency set.

- With no running containers, `wslc.exe stats --format json --no-trunc` succeeded
  with empty stdout. The previous collector produced the reported EOF error;
  the fixed collector completed and the TUI showed WSLC `0.0%` and `0B`.
- Two temporary, isolated containers were created from a cached image without
  mounts or network access. The fixed collector read both JSON records,
  nonzero memory values and internal processes. Both test containers were
  removed; existing containers were not started, stopped or removed.
- Ten consecutive host snapshots contained all expected Hyper-V counters.
  One interval overcounted root plus guest execution by about 0.046 percentage
  points and was correctly rejected. A bounded initial retry was added using
  the original baseline; regression tests also retain N/A on a failed or
  inconsistent retry.
- Four repeated one-shot starts and a 20-second TUI session completed without
  the host CPU partition warning. One one-shot run independently reported a
  transient additional-distribution collection failure; no claim of universal
  optional-collector availability is made.
- Before the version bump, 239 unit tests and two integration tests passed;
  four host/platform-specific tests were skipped by the normal test command.
  Formatting, Clippy with warnings denied, Windows GNU compile checks and the
  Linux release build also passed.

## Exact-artifact real-host checks

Both archives from the packaging run above were downloaded and checked for an
exactly matching SHA-256 sidecar and the expected executable/README/LICENSE
layout:

| Archive | SHA-256 |
| --- | --- |
| `wsltop-v1.0.1-x86_64-unknown-linux-gnu.tar.gz` | `c78de29909e4e1163c66406622cdaf08aafbbfea10d510f7958c4382296b4968` |
| `wsltop-v1.0.1-x86_64-pc-windows-msvc.zip` | `87ba883e9c94dfe6a8938d82a3ee3ac3e6a64b50d18e1c64b4ef87e8edbaad16` |

- Both extracted executables passed help/version and one-shot JSON collection
  with WSLC enabled and Docker disabled. Neither emitted the reported WSLC EOF
  or host CPU partition warning in these runs.
- The Linux archive passed all three `mcp_stdio` tests including the explicitly
  enabled live observation round trip. The Windows archive passed its two
  transport checks and a separate live round trip through all four tools,
  pinned-snapshot reuse and clean EOF. The Unix-only live test assumes
  `wsl_visible`; the Windows check instead verifies the specified `windows_host`
  CPU scope under `--wsl-only`.
- The native Windows MSVC TUI ran in a native ConPTY with read/write console
  handles for 16 seconds, accepted a tree-view toggle and `q`, and exited in
  25 ms. The alternate screen and original input/output console modes were
  restored. The two reported warnings were absent. A Unix PTY alone does not
  provide valid native Windows console handles.
- Controlled one-worker and four-worker CPU loads were measured using the Linux
  archive with `--wsl-only --cpu-scale host`. Both the WSL-visible and Windows
  host CPU counts were 16. Reported sums were about 6.35% and 25.40%; independent
  `/proc` process-time deltas agreed within 0.03 percentage points per worker.
  This checks normalization against the measured work, not exact equivalence
  with Task Manager's independently sampled total. Test workers were stopped.
- Docker 29.8.0 was reachable. A per-process `DOCKER_HOST` pointing to a
  nonexistent socket exercised graceful unavailable-daemon handling; collection
  still succeeded with no Docker rows. Restoring the inherited environment
  succeeded against the reachable daemon, which had no running containers.
  No daemon or existing container was stopped or reconfigured.

## Publication gates

This record does not publish a release. After reviewing and merging the PR,
tag the approved commit as `v1.0.1` using the
[publishing procedure](../publishing.md). Confirm the GitHub release assets and
crates.io publication, then check the WinGet workflow and its upstream PR.
The WinGet submission token must be configured for automatic submission; public
source indexing and installation/upgrade checks follow upstream acceptance.

The checks cover the reported regressions and representative release scenarios
on this host. They do not establish availability under every container topology
or workload. Public installation/upgrade, GitHub/crates.io publication and
WinGet acceptance remain post-merge/tag checks rather than completed actions.
