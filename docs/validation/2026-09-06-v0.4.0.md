## Publication

Prepare and review the release PR, including the packaging dry run, before tagging.
A `v0.4.0` tag push publishes GitHub release assets automatically. No tag or public
release is created during preparation. The workflow does not publish to crates.io.

## Publication and post-release checks

1. Merge the release PR and select the resulting clean commit. Repeat locked
   package/publish dry-run there; verify `.cargo_vcs_info.json` identifies that
   commit. Build release artifacts from that same commit.
2. On authorization to publish, create `v0.4.0` at that commit. Verify the resolved
   tag commit, GitHub Release tag, Cargo.toml/Cargo.lock version, and uploaded
   crate VCS metadata all agree. Publish the crate from that exact clean checkout.
3. Verify Release assets retain the documented filenames and sidecar format
   `<sha256>  <filename>`. Paste the handwritten release notes before the generated
   change list; use title `v0.4.0 — Native Windows support`.
4. Download public Windows assets with `Invoke-WebRequest`, verify `Get-FileHash`,
   run `Expand-Archive`, then run the extracted `wsltop.exe --version` and `--help`.
5. Download the public Linux archive and sidecar, run `sha256sum --check`, extract
   with `tar -xzf`, and run the extracted `./wsltop --version` and `--help`.
6. Test crates.io installation in an isolated prefix, preserving the user's
   installed binary: `cargo install --locked wsltop --version 0.4.0 --root /tmp/wsltop-v040-install`,
   then `/tmp/wsltop-v040-install/bin/wsltop --version`.

Public download/install and tag/crate/Release consistency checks remain pending
until publication; preparation results do not count as published-asset results.
