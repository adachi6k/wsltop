# v0.5.0 release preparation

Base: main `157e8c8`, including PR #30 and the host CPU/Windows timeout fixes
since v0.4.0. Release branch: `release/v0.5.0`.

This preparation changes versioning, release documentation, packaging verification
and compatibility tests only. It adds no runtime features. Candidate SHA and
executed gate results are recorded in the release-preparation PR so updating the
record does not change the candidate being measured.

## Compatibility scope

The public flat resource and attribution-tree JSON schemas and host-wide CPU
normalization remain compatible with v0.4.0. TUI display options do not enter JSON
serialization; a regression test compares flat and tree JSON before and after
classic/compact, color and width rendering. Runtime smoke also parses both forms.

Collector identities, attribution and sort semantics are unchanged. There are
intentional fixes already merged since v0.4.0: Windows command timeout/job cleanup,
Windows query-duration-aware refresh cadence, host physical memory observation
and shared history timestamps. These are not new collector types or JSON fields.
It would be inaccurate to claim that all collection timing is unchanged since
v0.4.0; release preparation introduces no further collector changes.

## Gates recorded against the candidate

The PR records metadata/version checks, formatting, unit tests, Clippy, release
build, Windows compile checks, clean `cargo package --locked` and
`cargo publish --locked --dry-run`, CI and the existing Release workflow dispatched
on the candidate branch. Packaging publication is skipped for workflow_dispatch.

Real-host checks use the extracted Linux and Windows MSVC artifacts, checking
compact/classic, color, flat/tree, sort, 75/90/120/200-column layouts, quit/Esc,
alternate screen/cursor and terminal input restoration. Any unverified portion
must remain unchecked in the PR rather than inferred from compilation.

## Publication is a separate gate

No public tag, GitHub Release or crates.io upload belongs to this PR.
After merge and explicit user approval:

1. Identify the merged commit and repeat clean package/publish dry-run and
   packaging checks. Confirm Cargo versions and `.cargo_vcs_info.json` agree.
2. Tag that exact commit `v0.5.0`, publish GitHub release assets and publish the
   crate from the same clean commit. Tag pushes automatically publish GitHub
   assets via the Release workflow; the workflow does not publish to crates.io.
3. Download public archives and SHA-256 sidecars again. Verify checksums, file
   contents and extracted `--version` / `--help` on both platforms.
4. Run `cargo install --locked wsltop --version 0.5.0 --root /tmp/wsltop-v050-install`
   in an isolated prefix and check its version. Do not replace the user's installed binary.

Keep archive names `wsltop-v0.5.0-x86_64-pc-windows-msvc.zip` and
`wsltop-v0.5.0-x86_64-unknown-linux-gnu.tar.gz`, with `.sha256` sidecars.
