# v1.1.1 release preparation — 2026-11-07

## Scope and compatibility

This patch includes the BuildKit attribution and sampling fixes from
[PR #82](https://github.com/adachi6k/wsltop/pull/82), plus the rmcp 3.8 dependency
update already merged since v1.1.0. Embedded BuildKit executor processes appear
under Docker, incomplete Docker observations remain unavailable, and
`--no-docker` preserves WSL CPU/RSS when cgroup metadata changes between samples.
Existing CLI options, JSON fields and units, and the four read-only MCP tools
retain their contracts. WSL kernel CPU remains inclusive while BuildKit overlap
cannot be resolved from common-window cgroup counters.

The candidate starts from main commit
`04759290ba9e8b2c18185d5dd0f50c1a0b0738bf`. Cargo metadata and the changelog select
version `1.1.1`. The changelog date records preparation in Asia/Tokyo; update it
if publication occurs on a later date.

## Real-host coverage

The [BuildKit review validation](2026-11-07-buildkit-review.md) records Windows
GNU execution with Docker Desktop, flat/tree membership without duplicate WSL
rows, and the `--no-docker` fallback. It also records regressions for changing
cgroup metadata and newly discovered distribution baselines. Those checks used
the implementation subsequently merged in PR #82, before this version bump.

The validation host runs Windows 11 Pro build 26200.9711 with 16 logical CPUs,
Ubuntu 24.04.4 LTS in WSL 2, WSL/WSLC 3.0.3.0, kernel 6.18.54.1-1 and Docker
client/server 29.9.2. Ubuntu and docker-desktop are running; the separate
GitHubRunner distribution is stopped.

### BuildKit and MCP

- A bounded BuildKit step ran one CPU worker from a cached image, with network
  access disabled for the build step. `docker ps` had no managed containers.
  Its three process PIDs and shared `/docker/buildkit/<executor>` cgroup were
  read directly from `docker-desktop` for comparison.
- Both artifacts passed flat and tree JSON checks: one Docker executor contained
  all three PIDs, with no duplicate WSL rows. The Linux flat sample reported
  6.261% host CPU and the Windows sample 6.258%; each summed RSS to 2,740,224 bytes.
- With `--no-docker`, all three PIDs appeared under WSL with the `docker-desktop`
  source and no Docker rows. CPU remained positive and RSS matched the sum above
  in both samples. These are separate windows, not exact CPU equality claims.
- Both artifacts exercised all four MCP tools while retaining one snapshot ID
  and checking the executor's three children. Setting `DOCKER_HOST` to an
  unreachable endpoint only for the test process preserved observed BuildKit
  rows while the Docker summary remained `null`. With the normal environment,
  Docker totals became available again. Both cases exited cleanly on EOF.
- The extracted Linux artifact also passed all three `mcp_stdio` integration
  tests, including the explicitly enabled live observation round trip.
- The expected unresolved-overlap warning was present; the WSL kernel
  observation remained inclusive while BuildKit rows were present.

### Interactive runtime

- The Linux artifact ran in a PTY with an explicit controlling terminal; the
  Windows MSVC artifact ran in a native ConPTY with read/write console handles.
  Each ran with Docker enabled and with `--no-docker`.
- The enabled runs displayed the controlled BuildKit executor under Docker.
  Disabled runs displayed its PIDs under WSL with the `docker-desktop` source.
  All four sessions accepted `t` to switch to tree view and `q` to exit with
  status zero. Alternate-screen exit and the original Unix terminal modes or
  Windows input/output console modes were restored.
- The first Linux probe rendered rows but lacked a controlling terminal for
  input. The probe was corrected and the interactive checks above were repeated
  successfully. No product changes were needed.

### Coverage limits

Distro startup during a sample and intermittent cgroup metadata are covered by
the automated regressions linked above. This run did not restart the user's
distros, exercise every Docker/WSLC topology or repeat unrelated process-action
workflows. The checks establish the changed collection paths and representative
release behavior on this host, not equality with independently sampled Task
Manager totals.
