# Issue #29: 最大2行のリソースヘッダー案

2026-09-11 / 初期検討。実装前の提案。

実装後の確定仕様は [実装記録](issue-29-implementation.md) を参照。以下は初期案の記録。現在は履歴を残したCPU/RAMの2行、Summary下の区切り線、枠なしの表、状態と操作の1行footerを採用し、履歴は120列以上で23点、80〜119列で15点、80列未満では非表示とする。

[Issue #29](https://github.com/adachi6k/wsltop/issues/29) は、htopのような色と、詳しいCPU/RAM表示を求めている。Issueのコメントでは、現在のシンプルな表示を残しつつ段階的に改善する方向が示されている。今回の制約は、上部の占有を最大2行とすること。

検討する価値はある。特に「どれくらい余裕があるか」を、リソース一覧を読む前に把握できる点が有用。初期案としては **Bの短いメーター付き2行表示** を推す。Aを簡素な表示として残し、Cは後続候補とする。

以下の数値と図は表示例。メーターや履歴の精度を示すものではない。ヘッダー専用の枠・タイトル行は追加しない。

## A: 数値中心 — 現在の表示から小さく拡張

```text
Host CPU  23.4% | RAM 12.3/32.0 GiB (38.4%)
tree | rows CPU: core | sort: cpu desc | refresh: 3s
```

- CPUとRAMの数字だけを淡く着色し、ラベル・区切りは控えめにする。
- 使用量・総量・割合を読めるので、容量を正確に把握しやすい。
- 横幅を取りにくく、白黒でも同じ情報が伝わる。
- 負荷の大きさを瞬時に比較するには、Bの方が向いている。

高さの小さい端末や従来表示を好む人に適する。既存の1行表示も選択肢として維持する。

## B: 短いメーター — 推奨

```text
Host CPU [##--------] 23.4% | RAM [####------] 12.3/32.0 GiB
tree | rows CPU: core | sort: cpu desc | refresh: 3s
```

- 1行目をホスト全体の状態、2行目を操作・表示状態に使う。
- CPUは割合、RAMは使用量/総量を数値で表示する。RAM割合は幅に余裕があるときだけ追加する。
- メーターは各8〜10文字程度。コア数やリソース数で行数を増やさない。
- 通常は落ち着いた色を使う。高い使用率の強調は補助表現とし、赤を障害の断定に使わない。
- 数値も常に残すため、メーターの粗さや色覚に依存しない。

「詳しさ」は、コア別の列挙ではなく、ホスト全体のCPU割合とRAMの使用量/総量で提供する。視線をほとんど移動せず、CPUとRAMの余裕を比較できる。

## C: 小さな履歴 — 瞬間的な負荷か継続的な負荷かを見せる

```text
Host CPU 23.4% ▁▂▆█▃▂ | RAM 12.3/32.0 GiB ▁▁▂▂▃▃
tree | rows CPU: core | sort: cpu desc | refresh: 3s
```

- 各6〜12サンプルの履歴を1行目に入れる。更新間隔3秒なら12点で36秒相当。
- CPUの一時的な跳ね上がりや、RAMの増加傾向が分かる。
- グラフは0〜100%の固定スケールとし、微小な変動の自動拡大はしない。
- 履歴の時間範囲、取得失敗時の空白、Unicode非対応時の代替表現が必要。
- メーターより説明と実装が増える。最初から標準にするより、後続の選択表示に向く。

## 比較

| 案 | 得意なこと | 横幅 | 追加の複雑さ |
|---|---|---|---|
| A 数値 | 正確な値を読む | 小 | 小 |
| B メーター | 現在の負荷を一目で把握 | 中 | 小〜中 |
| C 履歴 | 負荷の継続・変化を把握 | 中 | 中〜大 |

どの案でもホストRAMの収集追加は共通で必要。

## 共通の表示ルール

### 最大2行と幅の扱い

- 上部は既存の状態表示を含めて最大2行。画面の幅が狭くても折り返さない。
- 80列ではCPU/RAMと主要な設定を表示。幅が足りなくなったら、メーター、RAM割合、長い設定表記の順で縮める。
- さらに狭い場合も、CPU/RAMの数値と対象ラベルを優先する。設定はsortを優先し、更新間隔などを省略する。
- 高さが非常に小さい場合は1行の数値表示へ縮退する。切り替えの具体的な幅・高さは、40/60/80/120列の試作で決める。
- 更新ごとに桁幅が動かないよう、数値欄を固定幅にする。

### CPU/RAMの対象を揃える

- 通常時はWindowsホスト全体。CPUは既存のHost CPUを使い、全論理CPU合計で100%。一覧のCPU表示スケールから独立させる。
- RAMはホストの物理メモリを対象とし、使用量は「総量 − 利用可能量」とする提案。コミット量とは分ける。取得APIと意味は実装前に確認する。
- プロセス、WSL、コンテナのメモリ行を足してホスト使用量にしない。包含関係や共有メモリによって二重計上する可能性がある。
- フィルター、表示件数、ソートを変えてもホスト値は変えない。
- `--wsl-only` では初期実装はHost CPU/RAMを `N/A` とする。WSL内のメモリ値に黙って置き換えない。将来WSLサマリーを追加するなら対象名を明示する。
- 未取得・取得失敗は `N/A`。古い値を正常値として残さない。CPUが初回計測待ちでも、取得できたRAMは表示できる。

### 色はヘッダーから段階的に

- 最初はCPU/RAMメーター、数値、選択中のソート表示を着色する。画面全体の色数を増やしすぎない。
- RAM使用率の高さだけでメモリ不足とは判断しない。警告として扱うには別途根拠が必要。
- 一覧へ広げる場合は、CPU/MEM列やホスト・環境名の識別を優先し、行全体を塗り分けない。
- 白黒表示でも数値・ラベル・選択状態が伝わるようにする。明るい背景・暗い背景の両方で確認する。
- 色設定は `auto/always/never` と `NO_COLOR` 対応を候補とし、優先順位を仕様化する。ヘッダー形式と色の有無は独立させる。
- CLI候補は `--header classic|compact`。classicは既存1行、compactはBの2行。これは命名案で、初期実装で選択肢を増やしすぎない。

## 現在の実装からの進め方

確認したコードでは、`src/tui.rs` が上部1行・本文・下部1行を確保し、ヘッダーを文字列として描画している。`src/monitor.rs` の `MonitorSnapshot` には `host_cpu_percent` があるが、ホスト物理メモリの総量・利用可能量はない。一覧は文字列レンダラーの出力を `Line::raw` に変換している。

1. Bの80列・狭幅モックを作り、既存の1行表示と比較する。これをレイアウト選定の材料にする。
2. ホストメモリの任意値を収集モデルに追加し、ストリーム経由でTUIへ渡す。Windows実行とWSL実行の両経路で同じ意味の値を得る。既存の収集周期を利用し、描画時に問い合わせない。
3. ヘッダー専用の描画処理で2行と短縮規則を実装する。色付き部分はratatuiのSpan/Styleで表現する。
4. 一覧の色付けは別の小さな段階で進める。整形済み文字列へのANSI挿入ではなく、列の意味を保持する描画方式を検討する。

表示だけの変更で、JSONや通常のテキスト出力を不用意に変更しない。コア別使用率、swap、環境別内訳は初期範囲に含めず、必要性を個別に検討する。

実装時の検証は、幅・高さの縮退、0%/100%/N/A、取得失敗後の表示、フィルターとCPUスケールからの独立性、単色表示を中心にする。RAM収集は実ホストでも値の妥当性を確認する。

## 追加検討: Windows / WSL / WSLC / Dockerを識別する

ユーザーの追加提案を受け、環境別の識別を優先する。総使用量に加えて「どの環境が使っているか」が見えることは、wsltopの用途に合っている。以下のDを次の試作候補とする。

### D: CPUとRAMで1行ずつ使う — 更新後の推奨

```text
CPU 23.4% | Win 5.0%  WSL 10.0%  WSLC 2.0%  Docker 4.0%  ? 2.4%
RAM 12.3/32G | Win …G  WSL …G  WSLC …G  Docker …G
```

CPUの数値は排他的に集計できた場合の架空例。RAMの省略記号は設計未確定を示し、実際の画面では取得した値またはN/Aを表示する。

- 上部の2行をリソースに使い、tree/flat・sortなどは既存のResources枠タイトルへ移す。枠の行数は増やさない。
- 全体の値は左端に固定し、その後ろに同じ順序で環境別の値を置く。
- 色は環境の識別に使う。例えばWindows=青、WSL=緑、WSLC=紫、Docker=シアン。配色は仮で、明暗背景で検証する。
- 一覧の環境ラベルにも同じ色を適用する。上下の対応が分かることを優先する。
- 色だけに依存せず、常に環境名を併記する。Windows/WSLの省略形が紛らわしくならないよう、単文字化は避ける。
- 環境の色を負荷に応じて赤へ変えない。環境識別と負荷の強調は別に扱い、必要なら数値の太字などで表す。

### Hostという名前は全体に限定する

Host CPU/RAMはWSLやコンテナも含む全体。これと並べる内訳の名前はWindowsまたはWinとする。「Host + WSL + WSLC + Docker」と書くと、Hostに含まれる分をさらに足してよいように見える。

また、全体から識別済み環境を引いた残りをそのままWindowsと呼ばない。Windowsとして確認できた負荷と、不明・基盤処理・計測差による残りを区別する。

### 数値チップから始め、積み上げは条件付きにする

初期実装では環境ラベルと数値を横に並べる案が扱いやすい。ただし、数値を並べるだけでも加算可能に見えるため、包含する値には明示的な記号を付ける必要がある。例えば `WSL*` に対しヘルプで「Dockerを含む」と説明する。対応関係が不明なら、その不確実性を示し、排他的な内訳として表示しない。

将来、重複を除いた集計が成立すれば、Bのメーターを環境別の色で分割できる。積み上げは0〜100%のホスト容量を分母とし、CPU使用部分だけを100%へ拡大しない。未帰属分は灰色、未使用分は空欄とし、両者を分ける。

集計で確認すべき点:

- DockerがWSL内で動く場合、WSL全体とDockerは包含する。WSLCも実際の対応関係に基づいて扱い、分類名だけで排他性を仮定しない。
- コンテナ合計と内部プロセス、WindowsのVMホストプロセスとゲスト側の観測を重ねて足さない。現在のREADMEも親子CPUを加算しないと説明している。
- CPUは既存のホスト全体を分母とする値を利用する。採取時刻や取得範囲が異なるため、子の合計が親を超えた際に比率を黙って縮めて見せない。
- RAMはWindowsのプロセスメモリ、WSLの観測、コンテナ統計で定義が揃うかを先に確認する。物理RAMの排他的分割を保証できなければ積み上げない。環境別値は観測値として扱い、ヘルプに指標を明記する。
- 未取得と0は区別する。表示フィルターや上位N件によってサマリーが変わらないよう、集計は表示前のデータから行う。

### 幅の制約

80列では短い環境名と数値を優先し、メーターは省略可能とする。幅が広い場合だけ色分けメーターを加える。狭い端末では全体値を残し、環境詳細は一覧に委ねる。環境を省略した場合は `…` などで省略を示し、未表示を0と誤解させない。

## 今回の推奨

次の試作はDの「CPU1行・RAM1行＋環境別の色とラベル」とする。これにより、2行を超えずに消費元の識別まで提供できる。Bは全体値中心の簡素な候補として残す。

設計の次の焦点はレイアウトだけでなく、環境別CPUの排他的集計とRAM指標の定義。環境ラベルの統一色は先行して実現できるが、4分類の積み上げは集計の妥当性を確認したうえで採用する。

## 履歴表示の追加決定

ユーザーとの追加確認により、案Cの時間変化グラフも初期実装へ含める。Dの2行構成を保ち、各行のホスト全体値と環境別観測値の間に6〜12点のグラフを配置する。4環境のラベルを追い出さない範囲で幅を確保し、狭い場合はグラフを先に隠す。

CPU・RAMとも0〜100%の固定尺度とし、設定した更新間隔ごとの時刻スロットを使う。標準の12点×3秒で直近36秒。追加確認により、通常の計測待ちは前の値を保持し、明示的な取得失敗・取得不能だけを `!` で示す。初回計測前は空白。共通の固定時計で両グラフ全体を左へ送り、他の収集器の更新や画面再描画では時計を進めない。Windows収集も処理時間を含めた開始間隔へ修正する。
